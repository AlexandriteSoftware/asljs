# data-binding-typecheck-templates

Binding templates are not type-checked, so a binding that names a property the
model or the element does not have fails silently at run time.

Package: `data-binding`.

## Context

A template is markup in a TypeScript string, and its model has a real type next
to it, but nothing connects the two. In `libs/components/src/text-input.ts`:

```ts
type TextInputTemplateModel = Converted<{
  label: string;
  description: string;
// ...
  inputId: string;
```

```ts
template.innerHTML =
  `
    <div>
      <label
             data-bind-text="label"
             data-bind-prop-hidden="hideLabel"
             data-bind-for="inputId"></label>
```

`bindDataModel` reads each `data-bind-*` attribute at run time, resolves its
path against the model and writes the element. A misspelled path reads
`undefined`, and a property the element does not have becomes an expando. That
is how `<label data-bind-prop-for="inputId">` shipped in `asljs-components`: a
label has no `for` property, so the binding wrote `label.for` and the labels
were not associated with their controls. Five templates had it; the tests did
not notice until they asserted `label.htmlFor`.

Templates live in several places today: `template.innerHTML` in
`libs/components/src/text-input.ts` and `select.ts`, string properties of the
theme object in `libs/components/src/themes/bootstrap-theme.ts`, and
`e.innerHTML` in EdGames' `htmlapp/packages/app/src/ui/selector.ts`.
`bindDataModel(root, model)` accepts any object as the model, so passing the
wrong model fails silently too.

## Problem

Every fact a check needs is available before run time: the element type follows
from the tag (`HTMLElementTagNameMap`), the model type is declared, and each
binding names a path and a target. The type checker could reject `label.for =
model.inputId` (TS2339) or `model.lable` the moment the template is written, but
the template is a string it never sees, and finding templates inside TypeScript
strings would mean parsing the TypeScript and every way a string is assembled.

## Proposed behaviour

A template is a file, `*.tpl.html`, and a `data-binding` command compiles it to
`*.tpl.ts` next to it. The code imports the template from the `.tpl.ts` module,
and the package's ordinary `tsc` build type-checks it.

### The template file

The `<template>` element names its model type and the module it comes from:

```html
<!-- text-input.tpl.html -->
<template data-bind-model="./text-input.js#TextInputTemplateModel">
  <div>
    <label
           data-bind-text="label"
           data-bind-prop-hidden="hideLabel"
           data-bind-for="inputId"></label>
  </div>
</template>
```

### The generated module

`data-bind-compile` (the bin) writes one module per template. It carries the
markup as a string, so Node tests (JSDOM) and bundled apps import it like any
other module without a loader:

```ts
// text-input.tpl.ts - generated by data-bind-compile, do not edit
import { bindDataModel,
         type BindDataModelOptions }
  from 'asljs-data-binding';
import type { TextInputTemplateModel }
  from './text-input.js';

export const html = `...`;

export function createTemplate(
    doc: Document = document
  ): HTMLTemplateElement;

export function bindTemplate(
    root: ParentNode,
    model: TextInputTemplateModel,
    options?: BindDataModelOptions
  ): () => boolean;
```

The `import type` is erased, so a component that imports its own template does
not make an import cycle. `bindTemplate` takes the model type, so the wrong
model is a type error at the call site.

The checks are statements in a function that is never called, one per binding,
each with a comment that names the template line and attribute:

```ts
function check(
    model: TextInputTemplateModel
  ): void
{
  const e1 = document.createElement('label');

  // text-input.tpl.html:4 data-bind-text
  void model.label;

  // text-input.tpl.html:5 data-bind-prop-hidden
  e1.hidden = model.hideLabel;

  // text-input.tpl.html:6 data-bind-for
  void model.inputId;
}
```

`tsc` reports an error at the generated line, and the comment beside it names
the template line and attribute.

| Binding                   | Generated check                                                                                                                                       |
| ------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| `data-bind-text`, `-html` | `model.<path>` exists                                                                                                                                 |
| `data-bind-prop-<name>`   | `el.<name> = model.<path>` type-checks, so a missing property (`for`) or a wrong value type is an error                                               |
| `data-bind-<attr>`        | the value is a string, number, boolean or nullish                                                                                                     |
| `data-bind-class-<name>`  | `model.<path>` exists                                                                                                                                 |
| `data-bind-on-<event>`    | `model.<path>` is a function                                                                                                                          |
| `data-bind-context`       | the descendants are checked against `NonNullable` of the type of `model.<path>`, as a nested scope                                                    |
| a pipe                    | the name is a built-in or a declared custom pipe; the value type is not checked after a pipe, because `PipeFn` returns `unknown`, so only the path is |

### Where it runs

- The generated files are not committed. The package's `build` and `typecheck`
  run `data-bind-compile` first; a `--watch` mode serves `tsc --watch` and Vite.
  EdGames' web workflows already build the asljs packages they link, and run the
  command for their own templates the same way.
- `data-bind-compile` writes TypeScript only. It does not run `tsc`, so
  `data-binding` does not depend on `typescript`.
- The command reuses the binding grammar rather than copying it:
  `parse-data-model-binding.ts`, and the target mapping (`prop-`, `class-`,
  `on-`, `toPropertyName`) from `bind-data-model.ts`, moved where both the
  runtime and the command can import it.

### What it does not cover

Templates supplied at run time are not checked: a `<template>` the page provides
(`text-input.ts` looks one up before its default), and theme strings, unless the
theme moves them into `.tpl.html` files and imports them. For those, a runtime
warning when `data-bind-prop-<name>` names a property the element does not have
(`!(name in element)`) would catch the `for` case on its own.

## Points to settle

- Generic models, such as a `List` row whose `item` is the caller's type: a type
  parameter on the template that `bindTemplate` exposes, or rows checked against
  `unknown`, which checks only that paths are well-formed.
- The HTML parser: it must report source lines. `parse5` does and is light;
  JSDOM is heavy for a build tool. It is a `data-binding` dependency only the
  bin imports.
- Mapping `tsc` errors back to the template rather than relying on the comments,
  which needs the command to run `tsc` itself and so a `typescript` dependency.
- Whether the runtime warning for an unknown property ships with this or before
  it.

## Where

- `libs/data-binding/src/parse-data-model-binding.ts` - the binding grammar the
  command shares.
- `libs/data-binding/src/bind-data-model.ts` - how attribute names map to
  targets (`prop-`, `class-`, `on-`, attributes).
- `libs/data-binding/package.json` - the `bin` entry, and the parser dependency.
- `libs/components/src/text-input.ts`, `libs/components/src/select.ts`,
  `libs/components/src/list.ts`, `libs/components/src/themes/bootstrap-theme.ts`
  - the templates to move into `.tpl.html` files, and their model types.
- `libs/data-binding/docs/Bindings.md` - the template file, `data-bind-model`
  and the command to document.
